# 05 · 编码约定（避免乱码）

> 本工程历史上出现过三类乱码，都在这份文件里定下规矩，别再犯。

---

## 1. 唯一规范

**所有文本文件：UTF-8，不带 BOM。**

包括：`.v .cst .sdc .tcl .gprj .user .md .txt .py .ps1 .log .json`

例外：`.mem`（点阵/波形数据，纯 ASCII 十六进制）、`.fs .bin .db`（二进制产物）、`.vg`（网表，工具生成）。

---

## 2. 三类乱码的成因与对策

### ① 带 BOM 的 Tcl 脚本 → gw_sh 报错

**现象**

```text
gw_sh.exe : invalid command name "??pen_project"
    while executing
"??pen_project LQR_end.gprj"
    (file "build.tcl" line 1)
```

**成因**：`build.tcl` 被存成 UTF-8 **带 BOM**，Tcl 不跳过 BOM，把首字节当成命令名的一部分，
`open_project` 变成 `<BOM>open_project`。

**对策**：`build.tcl` 必须无 BOM。Gowin 自己写的 `.gprj` 也不要带 BOM。

```powershell
# 无 BOM 写法
$enc = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText("build.tcl", $content, $enc)
```

⚠ **不要用 `Set-Content -Encoding UTF8`**（Windows PowerShell 5.1 会加 BOM）。

### ② 工具日志是 UTF-16 / GBK，混进工程后像乱码

**现象**：`Compiling module ...` 之类的日志在 VSCode 里显示成方块或乱码。

**成因**：
- PowerShell 的 `>` / `Out-File` 默认写 **UTF-16 LE + BOM**；
- Gowin 控制台输出是 **GBK**，被按 UTF-8 解码会丢字。

**对策**：`tools/fix_encoding.py` 会扫描全工程，把 UTF-16 / GBK / 带 BOM 的文件统一转成 UTF-8 无 BOM。

```powershell
python tools\fix_encoding.py           # 只报告
python tools\fix_encoding.py --apply   # 实际改写
```

### ③ Markdown 围栏被破坏

**现象**：文档里出现 `` `	ext ``、`` `erilog `` 这种行，代码块不渲染。

**成因**：某次文本往返把连续三个反引号吞成了 `\t` / `\x0b`。

**对策**：`tools/fix_fences.py` 用状态机修复（块内单个反引号 → 收尾围栏；块外反引号+语言名 → 开头围栏）。

```powershell
python tools\fix_fences.py
```

```powershell
python tools\scan_encoding.py

# 出现 UTF-8-BOM / GB18030 / UNKNOWN 就要处理
```

---

## 4. 编辑器设置

| 编辑器 | 设置 |
|---|---|
| VSCode | 右下角编码选 **UTF-8**（不是 GBK，也不是 UTF-8 with BOM）；建议在工程根放 `.editorconfig` |
| 记事本（Win10+） | 另存为时选「UTF-8」，不选「带 BOM 的 UTF-8」 |
| Gowin IDE | 新建文件后另存为 UTF-8；若打开 `.cst` 显示乱码，先确认它是不是被别的编辑器改成了 GBK |

---

## 5. 已知的"看起来像乱码但其实是正常"的情况

在 **Windows PowerShell 里用 `Get-Content` 直接读 UTF-8 文件**，会按 GBK 解读，显示成
`鐗╃悊閲忔爣瀹?` 这种。这不是文件坏了，是**终端解码错了**：

```powershell
Get-Content src\LQR_end.cst -Encoding UTF8      # 正确
```

判断文件到底有没有坏，用 `tools/scan_encoding.py`，不要靠眼睛看终端输出。
